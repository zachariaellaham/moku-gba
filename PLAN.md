# MOKU — Tactics of Go · Build plan

Target: `dist/moku.gba`, a complete GBA Go game (campaign of 20 missions, sandbox with 5 AI
characters, 3 skins, 3 helpers, EN/FR, SRAM saves), verified by host unit tests and headless
mGBA ROM tests. Screens: `Go GBA Mockups.dc.html`.

## Toolchain (installed, do not reinstall)
- devkitARM r68 (gcc 16.1) under `$DEVKITPRO`; Butano 21 checked out beside this repository.
  Build env: `export DEVKITPRO=/opt/devkitpro DEVKITARM=$DEVKITPRO/devkitARM PATH=$DEVKITPRO/tools/bin:$DEVKITARM/bin:$PATH`
- ROM build: `make -j2` at repo root (Butano makefile, `-std=c++23 -O2 -fno-exceptions -fno-rtti`).
  Output `moku.gba` + `build/moku.elf`. `make dist` copies to `dist/moku.gba`.
- Host tests: `cmake -S tests/host -B build-host -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build-host && ctest --test-dir build-host`.
  doctest single header in `tests/host/third_party/doctest.h`.
- ROM tests: `tests/rom/harness/mokurun` (libmgba, ~4000 fps headless). Script language documented at
  the top of `mokurun.c`. Symbols: `arm-none-eabi-nm build/moku.elf > build/moku.sym`, then
  `symbols build/moku.sym` and `$g_moku_test+OFFSET` addressing. ROM `BN_LOG` output shows as `ROMLOG:` lines.
- Built on a two-core machine: one ROM build at a time, host builds `-j2`.

## Non-negotiable code rules
1. `src/go`, `src/ai`, `src/game/missions*`, `src/game/strings*` compile on the host with
   `g++ -std=c++20` AND on GBA. No Butano includes there, no floats, no heap, no exceptions, no RTTI,
   no `<iostream>`; `<cstdint> <cstring> <algorithm> <array>` are fine.
   Hot AI code lives in files named `*.bn_iwram.cpp` (Butano compiles them as ARM code into IWRAM).
2. Everything integer / fixed-point (scores in half-points `x2`, probabilities in permille).
3. Every public function of the engine has a host unit test. Every screen/feature has a ROM test.
4. Match the mockups (240×160): board fills the left 144 px, HUD is the right 88 px, dialogue
   box is the bottom 48 px. Palette: paper `#efe6d2`, ink `#1b1f2a`, wood `#d9a95a`, vermilion `#c23b2c`.
5. Commit after each milestone with a message that says what changed and why.

### Board rendering (decided)
Sprites are limited to 128, so stones are NOT sprites. The board is one 8bpp regular background whose
tiles are allocated at runtime (`bn::regular_bg_tiles_ptr::allocate`) and treated as a software
framebuffer for the 144×144 board area (18×18 tiles for 9×9@16px and 13×13@11px, 19×19 tiles for
19×19@8px). Stones/markers are blitted into an EWRAM shadow buffer and copied to VRAM when dirty.
Cursor, ghost stone, banners, particles, helper pop-in and text are sprites. HUD panel is a 4bpp
regular bg + text sprites. Skins = different palettes + stone/board tile art with identical layout.

### AI time slicing (decided)
`ai::Thinker::step(int work)` performs a bounded amount of work and returns whether the move is ready.
The play scene calls it repeatedly inside one frame while `bn::timer` says < 12 ms elapsed, so the
screen never freezes; a "thinking" animation runs meanwhile. HARD = up to 120 frames, MASTER = 300.
On the host the same Thinker is run to completion (playout caps make strength deterministic).
